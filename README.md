# update-flatpak-cli

A compiled, dependency-free reimplementation of
[`update_flatpak_cli.py`](https://gist.github.com/ssokolow/db565fd8a82d6002baada946adb81f68)
by Stephan Sokolow (SSokolow).

It generates launchers with **traditional command names for your installed
Flatpak applications**, so that

```console
$ flatpak run --file-forwarding org.gnome.Builder/… 
```

becomes

```console
$ gnome-builder
```

Run it with no arguments and you get the original behaviour:
`~/.local/bin/flatpak` is (re)populated with one launcher per installed
Flatpak application. Add that directory to the end of your `PATH` and Flatpak
apps behave like ordinary commands.

```console
$ update-flatpak-cli
Getting list of installed application/non-runtime packages...
Generating wrapper for com.github.tchx84.Flatseal...
Generating wrapper for org.gnome.Builder...
Generating wrapper for org.purei.Play...
...
Applications: 24   Launchers written: 26   Removed: 26   Skipped: 0   Collisions: 0   Warnings: 0
```

## Why a compiled version?

The original is a single Python file that depends on PyGObject, GLib, Gio and
the Flatpak GIR bindings, and imports `distutils` — **which was removed in
Python 3.12, so as written it no longer runs on a current distribution.** This
version:

* is one **static binary** (~1 MB, no shared libraries, no interpreter, no
  GIR typelibs, no `python3-gi`);
* starts in about a millisecond instead of paying for GObject introspection;
* reads Flatpak's on-disk layout directly instead of going through
  `libflatpak`, so it also works when inspecting another root (a chroot, a
  container image, a user's home from a recovery shell);
* is memory-safe by construction (it is written in Nim, which compiles to C
  but gives bounds checking, value semantics and reference counting) — see
  [docs/DESIGN.md](docs/DESIGN.md) for the security reasoning, which is
  deliberately in the spirit of the CERT C rules even though no C is
  hand-written.

Every behavioural rule of the original is preserved: the same name-derivation
heuristics in the same order, the same remapping tables, the same generated
bash, the same collision detection, and the same `$PATH` diagnostics.

## Install

Requires Nim ≥ 2.0 to build ([install instructions](https://nim-lang.org/install.html)).
There are no third-party packages — only Nim's standard library.

```console
$ make                 # static release build -> bin/update-flatpak-cli
$ sudo make install    # or: make install PREFIX=$HOME/.local
```

Then:

```console
$ update-flatpak-cli                     # generate launchers
$ export PATH="$PATH:$HOME/.local/bin/flatpak"   # put them on your PATH
```

Putting the generated directory **at the end** of `PATH` is deliberate: it
means a Flatpak can never shadow `ls`, `git` or anything else you rely on. The
tool warns you if the directory is ordered in a way that could.

Re-run it whenever you install or remove Flatpaks (or call it from a `systemd
--user` timer / a pacman or apt hook).

## Usage

```
USAGE
  update-flatpak-cli [OPTIONS]

With no options, this behaves like the Python original: it (re)generates a
launcher per installed Flatpak application in ~/.local/bin/flatpak.

OPTIONS
  -d, --bin-dir DIR       Output directory.  Default: ~/.local/bin/flatpak
      --system-root DIR   System Flatpak installation root.
                          Default: $FLATPAK_SYSTEM_DIR or /var/lib/flatpak
      --user-root DIR     User Flatpak installation root.
                          Default: $FLATPAK_USER_DIR or $XDG_DATA_HOME/flatpak
                          or ~/.local/share/flatpak
      --no-system         Ignore the system installation
      --no-user           Ignore the user installation
  -n, --dry-run           Report what would be done; touch nothing
      --no-prune          Keep existing generated launchers that are stale
      --prune-all         Delete every regular file in the output directory
                          (matches the original's sledgehammer behaviour)
  -f, --force             Overwrite files in the output directory that were not
                          generated by this tool
  -l, --list              List the app -> command mapping and exit
  -s, --strict            Exit 1 if any warning or collision occurred
  -v, --verbose           More detail
  -q, --quiet             Suppress progress output
  -h, --help              Show this help
  -V, --version           Show version
```

Exit status: `0` success, `1` fatal error (or warnings under `--strict`),
`2` usage error.

Handy invocations:

```console
$ update-flatpak-cli --list                    # review the name mapping first
$ update-flatpak-cli --dry-run --verbose       # see exactly what would happen
$ update-flatpak-cli --no-system               # only user-installed Flatpaks
$ update-flatpak-cli --bin-dir /tmp/launchers --system-root /mnt/chroot/var/lib/flatpak
```

## What a generated launcher looks like

```bash
#!/bin/bash
# AUTOGENERATED FILE! DO NOT EDIT!
# Generated by update-flatpak-cli for: org.gnome.Builder

# Unset LD_PRELOAD to silence errors about gtk-nocsd being
# missing from the Flatpak runtime
unset LD_PRELOAD

# Make arguments that are existing paths absolute
# and wrap them in the appropriate type of --file-forwarding
# wrapper tokens.
# (Necessary to make forwarding work reliably)
declare -a args
for arg in "$@"; do
    if [ -e "$arg" ]; then
        args+=("@@")
        args+=("$(readlink -f -- "$arg")")
        args+=("@@")
    else
        args+=("$arg")
    fi
done

# Use file forwarding to make paths Just Work
exec flatpak run --file-forwarding "org.gnome.Builder" "${args[@]}"
```

The `if [ -e "$arg" ]` dance is what makes `mpv ~/video.mkv` work despite the
sandbox: every argument that names an existing path is made absolute and
wrapped in Flatpak's `@@ … @@` file-forwarding tokens. Apps whose `.desktop`
file asks for URLs (`%u`/`%U`) get the `@@u … @@` variant instead.

## How command names are derived

Applied in this order, exactly as in the original:

| Step | Rule | Example |
|------|------|---------|
| 1 | Strip a script extension (`.sh`, `.js`, `.py`, `.pl`, `.rb`) | `86Box.sh` → `86box` |
| 2 | If the command *is* the app id, keep only the last component | `com.github.tchx84.Flatseal` → `Flatseal` |
| 3 | Lowercase it | `SweetHome3D` → `sweethome3d` |
| 4 | Strip a `_wrapper`/`-wrapper`/`_launcher`/`-launcher` suffix | `scummvm_wrapper` → `scummvm` |
| 5 | Apply an explicit remapping for this app id | `org.purei.Play` → `play_emu` |

The built-in remapping table exists because some packages ship genuinely poor
wrapper names, or would collide with an important command:

| App id | Exposed as | Because |
|--------|-----------|---------|
| `io.github.simple64.simple64` | `simple64` | ships `gui-wrapper.sh` |
| `org.godotengine.Godot3` | `godot3` | would collide with Godot 4 |
| `org.jdownloader.JDownloader` | `jdownloader` | ships `jd-wrapper` |
| `org.ppsspp.PPSSPP` | `ppsspp` | ships `PPSSPPDL` |
| `org.purei.Play` | `play_emu` | collides with SoX's `play` |

Some packages ship useful *secondary* commands; these get their own launchers
that pass `--command=`:

| App id | Extra commands |
|--------|----------------|
| `com.github.AmatCoder.mednaffe` | `mednafen` |
| `net.openra.OpenRA` | `openra-cnc`, `openra-d2k` |
| `org.atheme.audacious` | `audtool` |

Extending either table is a two-line change — see
[docs/CONFIGURATION.md](docs/CONFIGURATION.md).

## Differences from the Python original

Everything below is either a bug fix, a safety improvement, or something that
only appears under a new opt-in flag. Unadorned `update-flatpak-cli` behaves
like `python3 update_flatpak_cli.py`.

**Fixed**

* **It runs on Python ≥ 3.12-free systems at all.** The original imports
  `distutils.spawn.find_executable`, removed in Python 3.12.
* **Stale cleanup no longer deletes files it did not create.** The original
  removed *every* regular file in the output directory. This version removes
  only files carrying the `# AUTOGENERATED FILE! DO NOT EDIT!` marker, which
  also cleans up after the Python original since it wrote the same marker.
  `--prune-all` restores the old sledgehammer if you want it.
* **A hand-written file is never clobbered by accident.** If a file in the
  output directory is not ours, it is reported and skipped; `--force`
  overrides.
* **Launchers are written atomically** (temp file + `rename`) instead of being
  truncated and rewritten in place, so an interrupted run cannot leave a
  half-written launcher behind.
* **The "will mask / will be inaccessible" verdict is now actually computed.**
  The original called `find_executable()` twice and compared the results,
  which can never differ, so it always claimed the wrapper would be
  "inaccessible".
* **`$HOME` is used instead of the literal string `/home`** when deciding
  whether a shadowed `PATH` entry is user-owned, so the warning is correct for
  users under `/var/home`, `/Users`, NFS homes and so on.
* **Warnings go to stderr**, so stdout stays machine-readable (`--list` in
  particular).
* **Duplicate-name collisions are reported for both owners** and produce a
  non-zero exit status, so a cron job notices.

**Added**

* `--bin-dir`, `--system-root`, `--user-root`, `--no-system`, `--no-user`,
  `--dry-run`, `--no-prune`, `--prune-all`, `--force`, `--list`, `--strict`,
  `--verbose`, `--quiet`, `--help`, `--version`.
* Honours `FLATPAK_SYSTEM_DIR`, `FLATPAK_USER_DIR` and `XDG_DATA_HOME`, so it
  works on immutable distros, in containers and against mounted roots where
  the defaults do not apply, and so it can be tested without touching the real
  system.
* A user installation correctly shadows a system installation of the same app
  id, matching `libflatpak`'s precedence.
* Deterministic ordering (sorted by app id, then arch, then branch) and a
  summary line with counts.
* Refuses to operate on `/`, your home directory, `/usr`, `/usr/bin` or `/bin`,
  and requires an absolute output directory.

**Still true, unchanged from the original's "known shortcomings"**

* `file://` URLs are not recognised and wrapped in `@@u`.
* `--foo=/bar/baz` is not reparsed, so a path hidden in an `=`-style argument
  is not forwarded; use `--foo /bar/baz`.
* `.desktop` files installed *by* an app (secondary GUI apps) are not
  harvested automatically — hence the manual extra-command table.
* Flatpaks still do not install manpages.

## Development

```console
$ make test        # 50 unit tests + 75 end-to-end checks
$ make check       # type-check only
$ make debug       # build with runtime checks and stack traces
```

The unit tests (`tests/test_units.nim`) cover the key-file parser, the shell
word splitter, URL detection, every name-derivation rule and its ordering,
name validation, launcher rendering and file ownership rules, and `PATH`
analysis against synthetic trees.

The end-to-end suite (`tests/integration.sh`) builds throw-away Flatpak
installation trees in a temp directory, runs the real binary against them in a
hermetic environment, and checks generated file modes, contents and exit
codes — including a functional test that runs a generated launcher with a
stand-in `flatpak` executable on `PATH` to prove that arguments really are
forwarded the way the script claims.

Layout:

```
src/update_flatpak_cli.nim   CLI, orchestration, reporting
src/fpcli/ini.nim            GKeyFile-subset parser
src/fpcli/desktop.nim        .desktop Exec parsing, %u detection, shlex
src/fpcli/flatpak.nim        installation/ref discovery from disk
src/fpcli/naming.nim         command-name derivation + remapping tables
src/fpcli/wrapper.nim        launcher rendering, atomic writes, ownership
src/fpcli/pathscan.nim       $PATH search and shadowing analysis
tests/                       unit + integration tests
docs/DESIGN.md               architecture, parity notes, safety analysis
docs/CONFIGURATION.md        how to extend the mapping tables
```
