# Design notes

This document records how the compiled tool maps onto the Python original, why
some things were done differently, and what safety properties are claimed.

## 1. Parity map

| `update_flatpak_cli.py` | here | notes |
|---|---|---|
| `get_installed_packages()` — `Flatpak.Installation.new_system()/new_user()`, `list_installed_refs_by_kind(APP)`, `ref.load_metadata()`, `GKeyFile` | `src/fpcli/flatpak.nim` — `discoverApps()` | Walks `<root>/app/<id>/<arch>/<branch>/active → <commit>/metadata` instead of calling libflatpak. Same result, no GObject. |
| `GLib.KeyFile` parsing | `src/fpcli/ini.nim` | Subset: groups, `key=value`, `#`/`;` comments, backslash continuations, first-occurrence-wins. |
| `prepare_cmd_name()` | `src/fpcli/naming.nim` — `prepareCmdName()` | Identical five steps in the identical order. |
| `CMD_REMAPPINGS`, `EXTRA_COMMANDS` | `src/fpcli/naming.nim` — `CmdRemappings`, `ExtraCmds` | Same entries, same semantics, different spelling. |
| `wants_urls()` (Gio `DesktopAppInfo`, `shlex.split`) | `src/fpcli/desktop.nim` — `desktopFileWantsUrls()` | Own INI reader + own POSIX-ish word splitter; same `token.lower() == "%u"` rule. |
| `make_flatpak_cmd()` | `src/fpcli/wrapper.nim` — `renderWrapper()` | Same `flatpak run [--command=X] --file-forwarding "<ref>" "${args[@]}"`. |
| `make_wrapper()` | `writeLauncher()` + `emit` in `src/update_flatpak_cli.nim` | Same collision check, same `$PATH` warning, but see §3. |
| `find_executable()` (distutils) | `src/fpcli/pathscan.nim` — `findExecutable()` | Reimplemented because `distutils` is gone. |
| `main()` | `run()` in `src/update_flatpak_cli.nim` | Same order: discover → name → render → write → `$PATH` diagnostics. |

Ordering is observable through the collision behaviour, so it is preserved:
name heuristics run in the original order, and remapping is applied last.

## 2. Why read the disk instead of linking against libflatpak?

* It removes the only non-`stdlib` dependency, keeping the binary static and
  ~1 MB.
* It makes the tool usable against *other* roots (`--system-root`), which
  libflatpak's API does not offer: inspecting a chroot, a container image, or a
  mounted backup is a legitimate use.
* The layout (`app/<id>/<arch>/<branch>/<commit>/metadata` plus an `active`
  symlink) is a stable, documented on-disk contract; Flatpak itself has to keep
  it readable for `flatpak` and `ostree` to work.

The trade-off: if Flatpak ever changes that layout, this tool needs updating
where the original would not. To keep that failure loud rather than silent,
`discoverApps()` treats "no `app/` directory" as "installation not present"
(not an error) and a missing `metadata` file as "skip this ref", so a layout
change surfaces as "0 applications found" rather than a crash or a partial
silent result.

`activeDeployDir()` prefers the `active` symlink and falls back to the most
recently modified commit directory that contains a `metadata` file, which keeps
hand-assembled or partially-installed trees working.

## 3. Deliberate behavioural changes

1. **Marker-aware pruning.** The original deleted every regular file in the
   output directory because it had no way to know which files were its own.
   Since the original already wrote `# AUTOGENERATED FILE! DO NOT EDIT!` into
   every launcher, this tool can identify its own output — including output
   from the Python version — and prune only that. `--prune-all` restores the
   old behaviour.

2. **Refuse to overwrite unrecognised files.** Same reasoning as above, applied
   to writes rather than deletes. `--force` overrides.

3. **Atomic writes.** `writeLauncher()` writes `<name>.tmp<pid>` and renames it
   over the target. A rename within one directory is atomic, so an interrupted
   or crashed run can never leave a truncated launcher that would fail in a
   confusing way the next time the command is typed.

4. **Correct masking verdict.** The original computed the "already exists"
   warning by calling `find_executable()` twice and comparing the results,
   which is always equal, so it always printed "will be inaccessible". Here the
   position of the output directory in `$PATH` is compared with the position of
   the directory that owns the existing command.

5. **Exit codes.** A name collision (the "add a CMD_REMAPPINGS entry" case) now
   exits 1, and `--strict` promotes any warning to a failure, so the tool is
   usable from a timer or hook.

6. **Deterministic output.** Directory listings are sorted. The original's
   order came from libflatpak's internal ordering, which is stable but opaque.

## 4. Safety analysis

The original's `docs/LICENSE` worldview is "a small tool that writes files into
your home directory". The failure modes worth caring about are therefore:

**(a) Writing or deleting outside the output directory.** Inputs that reach a
path are app ids and `command=` values, both of which are package-controlled
(and a system installation can be a third-party repo).

* `validateCommandName()` requires a single, ordinary path component and
  rejects `.`, `..`, `/`, control characters, NUL, over-long names and names
  beginning with `-`.
* `hasTraversal()` rejects `.`/`..` path *elements* in the raw `command=` value
  before it is reduced to a basename. A separator alone is not rejected because
  `command=bin/foo` (a path relative to `/app`) is legitimate Flatpak metadata.
* The output directory itself must be absolute and is refused if it is `/`,
  `$HOME`, `/usr`, `/usr/bin` or `/bin`.
* Pruning and removal only ever touch regular files (never directories, never
  symlinks: `isGeneratedFile()` returns false for a symlink, so `removeFile`
  cannot be steered through one to another path).

**(b) Executing something unexpected.** The generated launcher is executed by
the user's shell.

* The app id and secondary command names are passed through
  `sanitizeForScript()`, which replaces `"`, `\`, `` ` ``, `$` and all control
  characters before interpolation. That neutralises both double-quoted shell
  expansion and — more subtly — a newline that would otherwise escape the
  comment line at the top of the file and inject a command.
* Everything the launcher interpolates at run time is quoted:
  `args+=("$(readlink -f -- "$arg")")`, and the array is expanded as
  `"${args[@]}"`.
* Launchers are created mode 0755 via an explicit permission set, not by
  inheriting whatever the umask happens to be.

**(c) Memory-safety and undefined behaviour.** No hand-written C, no manual
`malloc`/`free`, no pointer arithmetic. Nim compiles to C but provides bounds
and overflow checks (enabled by default; the release build here keeps range
checks on and enables `--opt:speed`, and `make debug` adds stack traces). The
classes of defect that CERT C rules CWE-119, CWE-416, CWE-476, CWE-787 and
CWE-190 describe do not exist in the source: there are no raw buffers, no
ownership to get wrong, and `Option[T]` is used instead of nullable pointers
(so a null dereference cannot happen).

Where the CERT C *spirit* does apply and was followed deliberately:

| Concern | Handling |
|---|---|
| Unbounded/unchecked input (STR31-C, STR32-C) | `splitLines`, slicing and indexing are all bounds-checked; malformed metadata is skipped, never fatal. |
| Path traversal (FIO02-C, CWE-22) | `validateCommandName()` + `hasTraversal()`; output dir allow-list. |
| TOCTOU on file creation (FIO01-C, CWE-367) | Files are created via temp-file + atomic `rename` in the same directory, then `chmod`; symlink targets are never followed for deletion. |
| Command injection (CWE-78) | `sanitizeForScript()` + explicit quoting of every expansion. |
| Ignoring return values (ERR33-C) | Every fallible operation (`readFile`, `writeFile`, `removeFile`, `createDir`, `setFilePermissions`, `moveFile`, `expandSymlink`) is wrapped in `try/except` and either reported or turned into a documented default. |
| Uninitialised data (EXP33-C) | Not possible: Nim zero-initialises object and seq locals. |

**(d) Trusting the `command` value's shape.** `flatpak run` refuses to launch an
app whose metadata is malformed, so a hostile value mostly costs the user a
launcher. The interesting case is a value that is a *valid* command in another
context (e.g. `rm`), which is handled by the `$PATH` precedence warning —
Flatpak launchers should be appended to `PATH`, not prepended.

## 5. Testing strategy

Two layers, both hermetic:

* `tests/test_units.nim` — module-level tests over the parser, the word
  splitter, URL detection, every naming rule and its order, validation,
  rendering, ownership rules and `PATH` analysis. Fixtures are real
  directories in a temp dir, including a synthetic Flatpak tree with an
  `active` symlink.
* `tests/integration.sh` — builds Flatpak trees, runs the real binary under
  `env -i` with a scratch `$HOME` and `$PATH`, and asserts on exit codes, file
  modes, file contents and messages. It includes a functional check: a
  stand-in `flatpak` that prints its argv is put on `PATH`, the generated
  launcher is invoked with a real file and a flag, and the suite asserts that
  the path was made absolute and wrapped in `@@ … @@` while the flag passed
  through untouched. Idempotence, marker-aware pruning, forced overwriting,
  dry-run, listing filters, `PATH` diagnostics and hostile-metadata rejection
  are all covered.

Nothing outside the temp directory is touched, so the suite is safe to run on a
machine with real Flatpaks installed.
